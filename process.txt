0. Before he arrives (5 minutes)

Make sure the EC2 instance is Running in the AWS console (start it about 10 minutes early), then:

bash
ssh -i ~/.ssh/pulseops-key.pem ubuntu@EC2_IP
cd ~/devops-fa2

Open a second SSH terminal and start traffic, so the graphs aren’t empty when you show them:

bash
cd ~/devops-fa2 && DURATION=1800 bash scripts/generate-traffic.sh http://localhost

Leave that terminal running for the whole session.

1. “Start the project”

Kubernetes keeps the app running all the time, so “starting” it means showing the cluster is up, then deploying the app with Helm:

bash
sudo systemctl status k3s --no-pager | head -5      # k3s service: active (running)
kubectl get nodes -o wide                            # node is Ready
TAG=$(git rev-parse HEAD)
GHCR_OWNER=parikshit245 bash scripts/deploy.sh "$TAG"

Say: “This deploys the app with Helm: a rolling update, then a smoke test that checks the frontend returns 200 and the API returns 401. If the new version doesn’t come up healthy, it rolls back automatically.” It should end with Deployed ... -> healthy. Because nothing has changed, it finishes in about a minute.

2. Kubernetes: show the live pods
bash
kubectl get pods -n pulseops -o wide
kubectl get svc,pvc,ingress -n pulseops
kubectl get deploy,daemonset -n pulseops

Say: “Six pods: frontend, backend, Postgres, Prometheus, Grafana and node-exporter. Services give them stable addresses, PVCs are the persistent disks, and the ingress routes port 80.”

Then the self-healing demo, which impresses examiners:

bash
kubectl delete pod -n pulseops -l app.kubernetes.io/component=frontend
kubectl get pods -n pulseops -w        # watch the new pod appear; Ctrl+C to stop

Say: “I deleted the pod. The Deployment noticed it had 0 of 1 replicas and created a new one automatically.”

If he asks for more detail:

bash
kubectl describe pod -n pulseops -l app.kubernetes.io/component=backend | tail -20   # events, probes
kubectl logs -n pulseops deploy/pulseops-pulseops-backend --tail=20                 # app logs
kubectl logs -n pulseops deploy/pulseops-pulseops-backend -c migrations             # DB migrations output

Don’t run kubectl top: metrics-server is disabled to save RAM, and Prometheus does that job.

3. Helm commands
bash
helm list -n pulseops                       # the release, its revision and status
helm history pulseops -n pulseops           # every deployment, including the auto-rollback
helm status pulseops -n pulseops            # resources + the help notes
helm get values pulseops -n pulseops        # settings this release was installed with (hides nothing secret-critical in output? see note)

helm get values prints the generated passwords, so don’t run it on a projector. Instead, show the chart files in VS Code: helm/pulseops/values-micro.yaml and helm/pulseops/templates/.

Say: “Helm packages all our Kubernetes YAML into one chart. Each deploy is a numbered revision. Here you can see a failed revision, followed by ‘Rollback to 6’, which happened automatically. I can also roll back by hand.”

To demo a manual rollback, take the revision number one below the current one from helm history:

bash
helm rollback pulseops <PREVIOUS_REVISION> -n pulseops --wait
helm history pulseops -n pulseops     # a new revision: "Rollback to N"
4. Prometheus and Grafana

First, show the raw metrics the backend exposes:

bash
BE=$(kubectl -n pulseops get svc pulseops-pulseops-backend -o jsonpath='{.spec.clusterIP}')
curl -s http://$BE:8000/metrics | grep '^pulseops_http_requests_total' | head

Say: “This is the /metrics endpoint. Prometheus pulls this every 30 seconds.”

Then show that Prometheus is scraping, from the terminal:

bash
curl -s 'http://localhost:30090/api/v1/query?query=up' | python3 -m json.tool | grep -E '"job"|"1"|"0"'

Then in the browser:

http://EC2_IP:30090/targets: all 4 targets UP.
http://EC2_IP:30090/alerts: the 22 rules, with MonitoredServiceDown firing for the broken test site.
http://EC2_IP:30300: log in as admin. The SRE Overview dashboard opens; then click through to Cluster & Node Resources.
5. PromQL in Grafana

In Grafana: left menu → Explore → data source Prometheus → switch the editor from Builder to Code → paste a query → Run query. Show these in this order:

#	Query	What to say
1	up	“1 means Prometheus could scrape that target, 0 means it’s down.”
2	sum by (route) (rate(pulseops_http_requests_total[5m]))	“Requests per second for each API route: the traffic signal.”
3	sum by (status) (rate(pulseops_http_requests_total[5m]))	“The same traffic split by HTTP status code: 200, 401, 404.”
4	histogram_quantile(0.95, sum by (le) (rate(pulseops_http_request_duration_seconds_bucket[5m])))	“p95 latency: 95% of requests are faster than this.”
5	pulseops:sli_availability:ratio_rate5m	“Our availability SLI, a recording rule. The SLO is 0.99.”
6	1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes	“Memory used on the EC2 machine, from node-exporter.”
7	sum by (pod) (container_memory_working_set_bytes{namespace="pulseops", container!=""})	“Memory used by each pod, from the kubelet.”

Another good move: on the dashboard, hover any panel → ⋮ → Edit. The real PromQL behind that graph appears at the bottom. Say: “Every panel is just a PromQL query.”
